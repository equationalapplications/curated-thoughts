## Problem

expo-llm-wiki shipped two releases that CT does not yet consume:

- **7.12.0** (2026-10-13, PR #281 / issue #280 PR-A): migration gate run before
  mutations, fail-closed policy, keyword-outage behavior pinned at all six search
  call sites, v14 legacy index, `setup({ migrations })` API.
- **7.13.0** (2026-10-14, PR #284 / issue #280 PR-B): FTS5 init state machine
  (B1–B6: budgeted drain modes + `setupBudgetMs` + schema **v15**, keep-map
  re-arm, chunked rebuild windows + fingerprint + orphan sweep, rename-retire
  resets, in-process VACUUM restart of a rebuilding index), plus drain-caller-ids
  fixes.

CT pins `@equationalapplications/core-llm-wiki` at **7.11.2** in three places
[V — grep on this branch's base `f4aa1ed`]:

1. `package.json` dependencies (`"7.11.2"`)
2. `package.json` → `pnpm.overrides` (`"7.11.2"`)
3. `src-tauri/src/db/schema_guard.rs:8` → `PINNED_CORE_LLM_WIKI_VERSION: &str = "7.11.2"`

Consequence: CT users do not get the migration gate or the FTS state machine;
every new CT feature built on wiki search inherits the pre-7.12 keyword-outage
behavior. Adoption follows the v3.5.1 precedent (Kurt, Sep 25 2026): bump the
engine package, keep the Rust schema-guard pin in lockstep, release at patch.

### Key verification result (shapes the whole approach)

The build-time guard `db::ddl_compat::tests::rust_llm_wiki_ddl_matches_core_llm_wiki_package`
extracts `setupDatabase` DDL from the *installed package's* `dist/index.js` and
compares it against the Rust constant `okf_ddl::LLM_WIKI_PACKAGE_DDL`. **Scope
pin (GLM r1, finding 2): the extractor captures only the FIRST
`await db.execAsync(\`...\`)` block after the setupDatabase marker
(`ddl_compat.rs:31-36`); 7.13.0's setupDatabase contains ~23 further execAsync
statements (conditional migrations, per-table index DDL, FTS pending-index DDL)
outside the mirrored batch.** The proven claim is therefore: *the mirrored
bootstrap batch is unchanged between 7.11.2 and 7.13.0* — the same Rust constant
passes against both pins [V — test run at 7.13.0 in the delivery worktree; the
7.11.2-side run is recorded in the controller session transcript for
2026-10-14, this thread]. **No conclusion is drawn about the unmirrored
statements** — they ride the bump unverified against the Rust mirror, which is
acceptable because the runtime FTS machinery owns them and the package's own
tests cover it.

### Runtime-diff risk (GLM r1, finding 3 — adopted)

7.13.0's FTS init state machine changes RUNTIME behavior the DDL mirror cannot
see, and one change destabilizes a path CT depends on:

- On first open of an existing vault, 7.13.0 may re-arm the FTS index into a
  "rebuilding" state with a bounded per-open budget (`setupBudgetMs`, default
  ~1.5s). **While rebuilding/failed, keyword search is unavailable**
  (`WikiSearchUnavailableError`); convergence happens across later opens and
  explicit no-arg `syncSearchIndex()` calls.
- CT's embed-failure fallback (`onRetrievalFallback`, `src/lib/wiki.ts:393`)
  presumes keyword search survives — the exact thing the rebuild window takes
  away. Affected: retrieval fallback, librarian/heal passes (they hold work and
  skip while keyword is down — held, not lost, per the package's own
  diagnostics).
- Every CT TS test mocks the engine package, so the vitest suite exercises zero
  7.13.0 runtime lines; the Rust gates never run JS. See Open Question below.

## Approach

One delivery, one PR, three file edits + lockfile, plus two runtime-safety
additions required by GLM r1 (Critical finding 1 — adopted in full):

1. `package.json` dependency: `core-llm-wiki` → `7.13.0`.
2. `package.json` `pnpm.overrides`: `core-llm-wiki` → `7.13.0` (forces the
   transitive `react-llm-wiki@7.11.2 → core-llm-wiki` edge up too — same mixing
   the v3.5.1 precedent accepted).
3. `schema_guard.rs` `PINNED_CORE_LLM_WIKI_VERSION` → `"7.13.0"`.
4. `pnpm-lock.yaml` regenerated by `pnpm install`.
5. **Host convergence scheduling** (`src/lib/wiki.ts`): 7.13.0's docs place a
   host obligation on long-lived processes — FTS rebuild work left after the
   bounded setup budget converges only via later opens or explicit no-arg
   `syncSearchIndex()` calls, and nothing in CT (or react-llm-wiki 7.11.2)
   calls it. Verified feasible in the pinned tree [V — runtime probe:
   `createWiki(...)` instance exposes `syncSearchIndex` as a function through
   the override mix]. Design (single-flight, no new deps):
   - after any successful `wiki.setup()` (the `wiki.ts:439` path and the
     re-create path at `wiki.ts:488`), fire-and-forget one no-arg
     `wiki.syncSearchIndex()` catch-up;
   - extend the existing `onDiagnostic` forward (`wiki.ts:396`) to also
     schedule a convergence retry when a keyword-unavailability diagnostic
     arrives (bounded backoff, single in-flight guard, dropped if a newer
     retry is pending).
6. **Unmocked runtime smoke test** (`scripts/runtime-smoke-clw.mjs` + CI step):
   every TS test mocks the engine package, so nothing exercises 7.13.0 runtime
   lines today. The smoke drives the REAL installed engine in Node over
   `node:sqlite` (bundled SQLite, FTS5-enabled; Node ≥ 22.5, run with
   `--experimental-sqlite` on the 22.x line) wrapped in the expo-sqlite
   adapter shape CT's Tauri adapter implements: `setup()` → ingest entries →
   `syncSearchIndex()` → keyword search returns hits → `WikiSearchUnavailableError`
   is NOT raised. This is the sentinel the mocked suite cannot be; it runs as a
   dedicated CI job step so a future engine bump that breaks real runtime
   behavior fails loudly at PR time.

Gates run locally before the PR is flipped ready (all [V], run in this order,
CI-exact flags):

- `db::ddl_compat` mirror test — passes at both pins (see above).
- `cargo test --lib db::` with `--features test-utils,mcp-server -- --test-threads=1`
  → 541 passed / 0 failed.
- Integration targets `wiki_graph`, `engine_source_ref_gate`, `okf_migration`
  (same flags) → 58 passed / 0 failed.
- `pnpm typecheck` → clean.
- `pnpm test` (vitest) → 597 passed / 1 skipped.

### Rejected alternatives

- **Family-wide bump** (`react-llm-wiki`, `schema-org-llm-wiki` → 7.13.0 too):
  larger diff, no evidence of need — typecheck and the full TS suite pass with
  only core forced up — and it deviates from the v3.5.1 precedent (bump only the
  package the train was about). Can ride a later train if react/schema-org
  surface changes require it.
- **Bumping `core-okf` / `schema-software-org`:** out of scope — they released
  7.13.0 in the same monorepo train, but neither is part of the core-llm-wiki
  adoption this delivery mirrors; precedent keeps unrelated pins untouched.

## Release mechanics

Commit type `chore(deps)` → analyzes as **patch** per the issue-#253 release
rule (`.releaserc.json` `releaseRules` `{type: chore, scope: deps, release:
patch}`) — verified rule present on this branch [V; GLM r1 independently
verified at base AND HEAD via `git show`]. The convergence-scheduling and
smoke-test additions ride the same PR under `fix(wiki)`-typed commits if kept
separate from the bump commit — no stranding risk either way: both subjects
release (patch floor), and the bump commit itself releases.
